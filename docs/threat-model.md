# kekkai threat model

Status: v0 draft for review gate 1 (ADR 0021). Scope fixed by ADR 0006. Section references
of the form §n point into [`docs/spec/protocol.md`](spec/protocol.md).

This document is generic by policy (ADR 0025): it speaks of roles and of "a host whose
disk is not encrypted", never of a named machine. Which hosts carry which role and which
accepted risks apply to which host live in the private deployment repository.

## 1. System

- **Nodes** terminate authenticated, encrypted tunnels between statically listed peers and
  route IP packets between the overlay interface and those tunnels. They run as a
  privileged service on Linux and macOS hosts: laptops on untrusted Wi-Fi, servers behind
  consumer routers or CGNAT, virtual machines on a hypervisor bridge, a public entry point.
- A **lighthouse** records where nodes are (observed and local endpoints) and tells a node
  where a peer is, so that two nodes behind NATs can hole-punch. It runs unprivileged on the
  public entry point.
- A **relay** forwards opaque payloads between two nodes that cannot reach each other
  directly. It runs unprivileged on the public entry point.
- **Configuration** is generated by Nix from one shared peer list: names, public keys,
  overlay addresses, static endpoints, inbound rules. Private keys are sops secrets placed
  on each host at boot. The deployment repository, the operator's workstation and the
  secrets store are trusted.
- The **control socket** (gRPC over a Unix socket, `0660 root:kekkai`) is read-only in v0.

## 2. Assets

| Asset | Where | Protected by |
| --- | --- | --- |
| Confidentiality and integrity of tunnelled IP traffic | the wire | §7, §8 |
| Peer authentication (only listed keys talk) | handshake | §4, §7.6 |
| Initiator key privacy against observers | handshake | §7.1 |
| Static private keys | host memory and secrets files | host (ADR 0017, 0018), out of the protocol |
| Unlinkability of a node's presence to strangers (silence) | every port | §16 |
| Availability of the mesh | lighthouse, relay, timers | partly (see §6 below) |
| Reachability of host services from the overlay | per-peer firewall | §15 |
| Metadata held by the infrastructure roles | lighthouse, relay memory | §13, §14 (bounded, never on disk) |

## 3. Trust boundaries

```
 untrusted LAN / Internet / CGNAT                          host
┌───────────────────────────────┐    UDP     ┌────────────────────────────────┐
│ passive or active network     │ ─────────▶ │ kekkai-node: parse (§5), mac1, │
│ attacker; strangers; scanners │ ◀──────── │ Noise, verify (§4), sessions    │
└───────────────────────────────┘            │  ▲ overlay traffic   ▲ status   │
                                             │  │ §11, §15          │ gRPC     │
┌───────────────────────────────┐            │  ▼                   ▼          │
│ lighthouse (metadata only)    │ ◀─ inner ─▶│ TUN interface    control socket │
│ relay (ciphertext only)       │  messages  └────────────────────────────────┘
└───────────────────────────────┘
```

Boundaries crossed by data in v0:

1. **Network → core**: every datagram. Nothing before a complete handshake is trusted;
   nothing after one is trusted beyond what the authenticated peer is allowed (§10.2, §11,
   §15).
2. **Core → tunnel interface**: only `ip_packet` bodies whose source belongs to the sending
   peer and that pass the inbound firewall.
3. **Node ↔ lighthouse**, **node ↔ relay**: ordinary peers at the handshake level; what
   they may say to a node is restricted by role (§10.2) and never includes an IP packet.
4. **Operator → core**: the configuration file and the private key, through the IO layer.
   Trusted.
5. **Local users → control socket**: members of the `kekkai` group read state. Nothing is
   mutable in v0.

## 4. Attacker classes

Each class states what the attacker can do, the guarantee kekkai gives against it, the
mechanism, and what is **not** guaranteed.

### 4.1 Network attacker (passive or active)

Position: shared LAN, Wi-Fi, ISP, CGNAT, Internet path, anywhere between two parties. Can
read, inject, modify, replay, reorder, drop, delay and redirect datagrams; can scan every
port of every host; knows the protocol; may know some or all public keys (they are in a
public repository only as examples; the deployment's are not published, but an attacker
who was once a peer, or who observed a host, may hold them).

Guarantees:

- **Confidentiality and integrity** of all traffic after the handshake: ChaCha20-Poly1305
  under keys from `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`, the WireGuard instantiation,
  whose analyses (Tamarin model, Dowling and Paterson) apply unchanged because the psk is
  zero and the prologue is a constant (§7.1). The payload security properties of `IK` in
  the Noise specification (§7.7 there) apply as tabulated: forward secrecy for transport
  data, and the known limit that message 1's sender authentication is vulnerable to
  key-compromise impersonation if the responder's static key leaks.
- **Mutual authentication**: the responder authenticates the initiator from `enc_static`
  and the `ss` term; the initiator authenticates the responder from `es`, `ee`, `se`
  against the static key it was configured with. Only keys in the receiver's list pass
  `verify` (§4).
- **Replay**: message 1 is bound to a monotonic per-sender timestamp (§7.4); message 2 is
  bound to a one-shot in-flight handshake by `receiver_index` and the ephemeral; data
  packets carry a never-reused 64-bit counter checked by a sliding window (§8.4).
- **Identity hiding**: a passive observer sees random-looking ephemerals, ciphertexts and
  32-bit indices. The initiator's static key is hidden from a passive observer; the
  initiator's address is not (the outer `type` byte is in clear, as in WireGuard), and
  anyone who knows the responder's public key can confirm the responder's identity through
  `mac1` (as in WireGuard). An active
  attacker who sends a message 1 to a node learns nothing: without the node's static key it
  cannot even form `mac1`; with it, the handshake fails at `verify` and nothing is sent.
- **Silence**: a kekkai port never answers a datagram that does not complete the full chain
  of §5.6 and §7.6 (§16). A scanner sees a closed-looking UDP port that never answers; a
  host without the peer's key cannot distinguish a kekkai host from a host dropping UDP.
- **Header tampering**: the outer header is not authenticated (§5.4); a changed
  `receiver_index` selects another session whose key fails the AEAD, a changed `counter` is
  a different nonce and fails the AEAD, a changed `version` or `type` is dropped before
  parsing. `mac1` covers the whole handshake message before it.
- **Reflection and amplification**: a `handshake_init` (151 bytes) earns at most one
  `handshake_resp` (92 bytes), and only from a listed key with a fresh timestamp. Nothing
  is amplified.

Not guaranteed:

- **Traffic analysis**: sizes, timing, the fact that two addresses talk, and the inner
  type boundaries implied by sizes (a keepalive is always 33 bytes) are visible. No
  padding, no cover traffic (ADR 0009).
- **Volumetric denial of service**, and **CPU exhaustion of a responder** by a flood of
  message 1s from someone who knows its public key: each costs the responder two X25519
  operations after the `mac1` check. The cookie mechanism is reserved
  (`cookie_reply`, `mac2`, §5.3, §5.5) and not implemented in v0. `mac1` is **not**
  authentication: it only prices a probe at one keyed hash and stops attackers who do not
  know the public key.
- **Denial of service by path manipulation**: an attacker on the path can drop traffic,
  break a direct path and force a relayed one, or spoof source addresses so that a node's
  endpoint moves. Endpoint roaming (§12.4) only follows **authenticated** packets, so a
  spoofed address never receives plaintext; the worst case is a stale endpoint until the
  next authenticated packet or rediscovery, that is denial of service.
- **A replayed message 1 after a responder restart** is accepted once (the `last_timestamp`
  table is in memory, §7.4), as in WireGuard; it yields a `next` session nobody can confirm
  (§8.3) and that expires.

### 4.2 Compromised lighthouse

Position: an attacker controls the lighthouse process or host, including its private key.

Learns: the public keys of the nodes that register and query, their observed and local
endpoints, when they are present (`last_seen`), who asks about whom. Nothing is persisted;
logs carry aggregate counters only (§13.2).

Cannot: read, modify or inject traffic between nodes (it never holds a session key of a
node pair: lighthouse messages are inner messages of the node↔lighthouse session, and the
lighthouse core has no `relay_forward` or `ip_packet` path, §10.2); impersonate a node
(it has no node's static key, and `IK` authenticates both sides); make a node talk to an
unlisted key (`lighthouse_punch` and `lighthouse_query_reply` only widen candidates for a
**configured** peer, §13.3, and the handshake with that peer still authenticates it).

Can: withhold or lie about endpoints, send punches to arbitrary configured peers, answer
"unknown". All of this is denial of service or wasted handshakes towards wrong addresses,
each of which is silent and costs the recipient at most one `mac1` check. A lying
lighthouse can also direct a node's message 1 at an attacker-chosen address, which reveals
to that address that the node exists and the size of a message 1, and nothing more.

In v1 the lighthouse will distribute CA-signed certificates that each node verifies itself;
its trust level does not grow (ADR 0007, 0012).

### 4.3 Compromised relay

Position: an attacker controls the relay process or host, including its private key.

Learns: the public keys of both ends of each relayed flow (`to_pubkey`, `from_pubkey`),
their source addresses, packet sizes and timing, per-sender byte and packet counters.
Nothing is persisted; logs carry aggregate counters only (§14.2).

Cannot: read or modify the relayed traffic. The payload it carries is a complete outer
message of the `A↔B` session, encrypted under keys the relay never derives (double
encryption, §14). It cannot inject: an injected payload fails `A↔B` authentication. It
cannot move a node's endpoint: packets received through `relay_forwarded` never update an
endpoint (§12.4). It cannot make a node use it for an unlisted peer (§14.1).

Can: drop, delay, reorder, duplicate (absorbed by the replay window), or refuse to forward:
denial of service of the relayed path only; the direct retry (§12.3) is unaffected because
it does not pass through the relay.

Structural guarantee: the relay's state holds no key material of a node pair, and
`kekkai-relay` depends on no tunnel decryption code path; checked by a unit test, a
dependency check and a packet capture in milestone v0.5 (ADR 0014, 0020).

### 4.4 Compromised node

Position: an attacker holds a legitimate node's private key, or controls the node's host.

Can: do everything that node may do. It reaches, on every other node, exactly what that
node's `allow_inbound` rules for the compromised peer allow, plus ICMP, plus replies to
flows the victim node initiated towards it (§15). It can send any IP packet whose source
is one of its own overlay addresses (§11 drops the others, so it cannot spoof another
peer). It can query the lighthouse about any listed key and learn its endpoints (ADR
0012 accepts this in v0). It can use the relay towards any listed peer.

Cannot: read traffic between two other nodes (no shared key); impersonate another node
(no key); escape its overlay addresses; bypass another node's firewall except through the
rules that node granted it; cause another node to accept a packet from an unlisted key.

Revocation in v0: remove the key from the shared peer list and redeploy; every other
node's `verify` then rejects it and its sessions are discarded at reload or restart
(§4). Until the redeploy it remains a legitimate peer: the window between detection and
redeploy is accepted in v0.

### 4.5 Local attacker on a host

Not a protocol attacker; recorded for completeness. A process running with the node's
privileges reads the key and the plaintext: out of scope (ADR 0006). An unprivileged local
user sees only what the control socket's group grants, which is read-only state including
public keys, endpoints and counters, never key material or payloads (§16).

## 5. Accepted risks in v0

| Risk | Why accepted | Mitigation path |
| --- | --- | --- |
| Key at rest readable by whoever holds the disk of a host without full-disk encryption (on macOS the decrypted key is written under `/var/run`, which is on disk; on Linux `/run` is tmpfs but the sops age key is on disk) | A one-person homelab; the affected hosts are known to the operator and recorded privately | Wrap the key at rest and unwrap at start (Secure Enclave on macOS, TPM2 and `systemd-creds` on Linux), ADR 0017; the core already takes an opaque `StaticKey` |
| Responder CPU exhaustion by handshake floods from someone who knows a public key | No public key is published; the entry point's exposure comes with gate 2 only; the `mac1` check already removes blind floods | `cookie_reply` and `mac2` are reserved (§5.3, §5.5) |
| Replayed message 1 accepted once after a responder restart | WireGuard's accepted behaviour; the resulting session cannot be confirmed by the replayer | None planned |
| Wall clock going backwards blocks a node's own initiations until it catches up | Hosts run NTP; the node still answers its peers; a warning is logged after `REJECT_AFTER_TIME` | None planned; a persisted timestamp would be the alternative |
| Traffic analysis, no padding | Not a goal for v0 | Padding is a format change (wire version) |
| A compromised node keeps its access until redeploy | Static configuration is the source of truth | Certificates with expiry and revocation in v1 (ADR 0027) |
| Any listed node may learn any other listed node's endpoints through the lighthouse | Small closed membership | Mutual-listing or group policy with v1 |
| The relay's payload size bound (1313 bytes) and per-sender counters are the only quota by default | Only listed keys can relay; abuse means a compromised node | Per-sender rate limit, configurable (§14.2) |
| Stray non-SYN TCP segments from a peer reach the kernel and elicit a reset over the tunnel | Stateless TCP check, no connection tracking | Connection tracking later (ADR 0027) |
| Late replies of a UDP flow evicted from a full flow table are subject to the rules | Bounded memory for the iOS target | Larger configured table on hosts that need it |

## 6. Availability

Availability is best effort. What the design does provide: persistent keepalives keep NAT
mappings and sessions alive and detect a dead peer within 15 s (§9); sessions survive
reordering and duplication within the window; a lost direct path falls back to a relay
within `DIRECT_PATH_TIMEOUT` and retries directly every `DIRECT_RETRY_INTERVAL`; a node
whose lighthouse disappears keeps every established session and re-registers when it
returns; the lighthouse's and relay's loss of memory on restart is repaired by the next
keepalive. None of this holds against an attacker who controls the path or floods the
link.

## 7. Assumptions

- The primitives of §2 are secure as instantiated; `snow` and the RustCrypto crates
  implement them correctly. The hand-written glue around them is what the reviewers of
  gate 1 examine against this document and the vectors (§19).
- The host's CSPRNG is sound (ephemeral keys, indices, jitter).
- The suspend-aware monotonic clock does not go backwards. The wall clock may be wrong by
  any amount.
- The deployment repository, the secrets store and the operator's workstation are not
  compromised; a compromise there is a compromise of every key.
- Private keys are generated by `kekkai keygen` from the host's CSPRNG and never reused
  across roles.

## 8. What reviewers should look at (gate 1)

1. §5.5 `mac1`: the key derivation, the coverage (every byte before the slot), the
   constant-time comparison, and that it is checked before any Diffie-Hellman but is never
   treated as authentication.
2. §7.4 TAI64N: encoding, alignment, the bytewise comparison, the update-on-success rule,
   the per-static-key table, and the consequences of a stepping wall clock.
3. §6 TLV codec: canonical form, the critical bit including its effect on ordering,
   truncation handling, and that a parse error always ends in silence.
4. §7.1 and §7.2: that the `snow` instantiation (prologue, psk at position 2, pre-message)
   is exactly WireGuard's handshake with a zero psk, and that `handshake.json` is
   consistent with `noise_ikpsk2.json`.
5. §8: nonce formation (big endian on the wire, little endian in the nonce), counter
   monotonicity by construction, the window's boundaries, session slots and confirmation,
   and the rekey and reject timers against WireGuard's.
6. §16: that every drop condition is listed and reachable, and that no path produces
   output before full authentication.
